# 交付与截止时间协议

本协议用于真实竞赛、课程提交或其他有明确截止时间的数学建模任务。最高目标不是生成理论上最完美的局部内容，而是在截止时间前可靠地产出并成功提交当前条件下质量最高的合规成果；当二者冲突时，可提交性优于局部完美。

本文所称“可提交版本”是指文件层面完整、可打开且满足已核验硬约束的候选成果，不改变根目录 `使用指南.md` 规定的使用边界。用户仍须亲自理解、核对、修改并承担最终提交责任。

## 一、先核验时间与提交约束

1. 读取当前系统时间、时区和剩余时间。
2. 从目标竞赛当届官方网站核验截止日期、时区、允许文件格式、文件数量、大小限制、命名规则和上传入口。往届日期和用户记忆只能作为检索线索，不能替代当届官方信息。
3. 记录“官方截止时间”和更早的“内部内容冻结时间”“最迟安全导出时间”。内部时间必须为异常处理、重新导出和人工上传留下显著缓冲。
4. 无法核验官方时间时，明确标记未知项并请用户确认；不得把推测写成已确认事实。

## 二、尽早验证完整链路

在主要内容尚未全部完成时，先用最小真实样例走通一次完整链路：

`代码 → 结果表/图 → 论文源文件 → DOCX/PDF → 支撑材料 → 压缩包 → 人工打开检查`

不得假设 Markdown 转 DOCX、LaTeX 转 PDF、代码转图表等步骤最后很快就能完成。格式转换、文件生成、字体和公式渲染、人工检查、压缩、上传及提交确认都是正式任务，不是零成本的收尾动作。Agent 不能代替用户完成登录、上传或最终提交确认时，仍须明确提醒并给出待办清单。

## 三、始终维护可立即提交的版本

按以下状态推进，并为每个已通过状态保留独立快照或副本；条件允许时记录文件清单和 SHA-256：

1. **Checkpoint V1**：首次完整、可打开、满足已知硬约束且包含全部必需文件的可提交版本。优先尽早产出，不等待所有局部优化完成。
2. **Checkpoint V2**：在不破坏 V1 的前提下完成受控优化，并重新运行受影响的门禁。
3. **内容冻结**：停止改动正文、数据、图表和引用，只允许修复会阻止提交的确定性问题。
4. **最终导出**：从已冻结内容生成正式 DOCX/PDF 和支撑材料包。
5. **完整性与合规检查**：核对文件可打开、可解压、命名、格式、大小、页数、内容一致性和官方要求。
6. **人工上传与确认**：提醒用户预留登录、网络、上传、平台校验和最终确认时间；未经用户或平台证据确认，不得声称已经提交。

Checkpoint V1 出现后，任务原则上不得再次回到没有任何可提交版本的状态。后续修改应在副本、分支或新版本上进行，已验证的 V1 不得被原地覆盖。

## 四、按异常而非最快耗时预留缓冲

对格式转换、复杂排版、文件生成、网络上传、第三方工具调用、AI 调用和长任务，按“发生一次异常并完成排查、重试后仍能提交”安排缓冲，不按理论最快耗时排期。剩余时间不足以覆盖失败和回滚成本时，缩小修改范围，优先保护当前可提交版本。

临近内容冻结时间或最迟安全导出时间，每次准备进行新修改前必须先问：

> 如果这次修改失败、耗时远超预期或工具出现异常，我手里的版本还能否按时提交？

若答案是否定的，默认建议不执行该修改；保留当前可提交版本，只处理会直接阻止合规提交的问题。

## 五、提交前最低检查

- 官方截止时间、时区和提交入口已核验。
- Checkpoint V1 仍可独立打开和提交；V2 或最终版失败时可立即回退。
- DOCX/PDF 已实际打开并抽检公式、图表、分页、字体和参考文献。
- Word 文本中没有残留 Markdown 标记或临时占位符，包括 `**`、反引号、标题 `#`、表格竖线、公式定界符 `$`/`$$`、列表标记和 `[待补充]`；确属正文内容的符号已人工复核。
- 支撑材料清单、文件名、扩展名、大小和压缩包目录结构符合当届规则，压缩包已实际解压验证。
- 已明确提醒用户完成登录、上传、平台校验、最终提交和提交成功凭证留存。
